# Spec review: Conversation grouping in the message list
## Verdict
NEEDS CHANGES — cross-folder copies can disappear during conversation actions, and repeated jumps within one mounted thread can show the wrong message.
## Findings (confidence 7+)
[P1] (confidence: 10/10) Design: Actions on a conversation — “Messages of the thread in other folders ... are not touched” fails when the same Gmail `msgId` is loaded in Inbox and Sent: `GmailAPIManager.swift:747,802-813` removes every folder copy during archive/delete/spam and move-to-Inbox, then creates only the destination copy — preserve unaffected folder copies and test archiving an Inbox+Sent message leaves its Sent row present; keep the user choice `Decisions: What do Archive / Delete / Spam / Move-to-Inbox act on when invoked on a grouped conversation row? (user)`.
[P1] (confidence: 9/10) Decisions: How should a notification/search jump to an older member of a conversation be handled in the detail panel? (auto) — the proposed `.id(accountId_threadId)` and thread-key reload leave `ThreadDetailView` mounted when a second jump changes only `focusMessageId`; the specified scroll runs only after page load, so it never focuses the second target (or returns to the top when focus becomes nil). `ThreadDetailView.swift:166-179,237-271` has no focus-change path — scroll on every focus change, including nil, after WebKit is ready; verify two successive jumps within one thread and then a row tap.
[P1] (confidence: 9/10) Testing — the new `GmailAPIManager.apply` test resolves partial-failure behavior but still cannot prove “all entry points ... go through this path”: `MainView.swift:208-220,382-409,589-597,818-862` owns context-menu, keyboard and detail-button routing, while `MessageListTests.swift:149-243` only call standalone closures — add a testable action-target resolver asserting both folder-local IDs, and a manual check for each entry point that both members move while a Sent member remains; this is the still-open UI-routing part of the previous review finding.
[P2] (confidence: 9/10) Testing — no check covers the new `onReselect` path or proves that selecting a two-member row calls mark-read for *both* unread members; the manual check only says “marks both read” and the existing `GmailAPIManagerTests.swift:337-385` cover one message — add an XCTest with two unread thread members and `MockURLProtocol` asserting two distinct modify requests, plus a manual check where a new unread member joins the selected row and tapping that row clears its bold state.
[P2] (confidence: 8/10) Testing — `ConversationTests` omits the explicit same-thread/different-folder boundary, and “a row with two messages renders one row” does not verify the required count capsule or bold styling when only an older member is unread — add an XCTest with one thread in Inbox and Sent expecting two conversations, and a `MessageListTests` view check with two members expecting one row, count 2, and unread styling.

## Section notes
### 0. Scope challenge
Existing `UnifiedMailbox.emails`, `MessageList`, `MainView` selection/actions, manager mutations, and `ThreadDetailView` cover the path; `Dictionary(grouping:by:)` is built in. The design touches more than eight files. A smaller variant could put the type in an existing model file, derive the shared projection from `emails`, and extend existing test files, but the recorded user scope choice keeps the published projection and new files. Detail eligibility could be deferred only by revising its recorded decision. The new source files require project registration, now specified; there is no separate distribution artifact. The cross-folder and focus failure paths need full handling.
### 1. Requirements
The promise that other folders stay untouched conflicts with the per-message move implementation. “After the page loads” admits an initial-load-only reading and a reload-on-every-selection reading; the latter is required for successive jumps. No placeholders remain. The previous same-row reselect, 404, and account-qualified identity ambiguities are resolved in the revised text.
### 2. Scope
The Non-goals clearly exclude Drafts grouping, Outbox, search-result grouping, count changes, batch API calls, and fetch/schema changes. Grouping, multi-member actions/read state, and detail eligibility are separable work, but the user explicitly chose to keep them in one spec; no repository fact makes that choice unworkable. The previous scope finding is resolved by that decision.
### 3. Feasibility
Resolved from round one: project-file registration, locally loaded detail eligibility, account-qualified thread identity/cache, the reselect callback, the full-sort rebuild path, 404 semantics, stable tie order, corrected complexity, and `moveEmailInMemory` metadata. The existing `performMove`/`removeEmailFromMemory` path still deletes other folder copies, and a mounted `ThreadDetailView` still needs a focus-change trigger. Existing `ThreadHTMLTests` in `ViewTests.swift:511-580` proves app-side JavaScript runs under the page policy, so the proposed scroll method is feasible.
### 4. Testability
The revised manager test covers the prior partial-failure gap, and the older-member navigation/reply and two-account checks address the prior missing cases. UI routing remains unproved; tests also omit multi-member read/reselect, cross-folder isolation, and row badge/unread rendering. Each has a concrete check in the findings above. `./scripts/test.sh` uses XCTest and rejects zero-test runs; no tests or builds were run for this review.
### 5. Decisions
The auto folder, newest-row, folder-local, selected-email-ID, and locally loaded detail choices fit the repository. The auto older-member-focus decision is unmet for repeated jumps in one mounted thread. The user choices are implementable, but their folder-local action choice needs the cross-folder preservation above.
