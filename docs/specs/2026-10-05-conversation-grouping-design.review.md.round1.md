# Spec review: Conversation grouping in the message list
## Verdict
NEEDS CHANGES — the new files will not build as specified, and several selection and thread-detail guarantees are not met by the proposed paths.
## Findings (confidence 7+)
[P0] (confidence: 10/10) Design: Model / Testing — `Conversation.swift` and `ConversationTests.swift` are new files, but `Aerio.xcodeproj/project.pbxproj:193-220,396-467` explicitly lists each source and test file; neither file will compile or run merely by creating it — require project file references and Sources entries for both targets, or place the code and tests in existing compiled files.
[P1] (confidence: 10/10) Decisions: When should the detail panel show ThreadDetailView (all thread messages) instead of the single-message view? (auto) — the proposed predicate sees only loaded emails; `GmailAPIManager.swift:1081-1085` counts local rows, so a thread with one loaded member and older members beyond the current page opens the single-message view despite the recorded “whenever the thread has >1 message” choice — resolve multiplicity on selection through the existing `fetchThread` path or revise the decision to mean locally loaded messages.
[P1] (confidence: 9/10) Design: Detail panel — retaining `.id(email.threadId)` leaves `ThreadDetailView` mounted when moving between accounts that share a threadId, although the model explicitly treats those as different conversations; `ThreadDetailView.swift:178` reloads only on threadId changes, and `:253` also omits accountId from its HTML cache key — key the view and caches by `(accountId, threadId)` and test switching between accounts with the same threadId.
[P1] (confidence: 9/10) Design: Selection state / Detail panel — “Notification click, search jump and pinnedEmailId keep working unchanged” is false for a jump to an older member: `MainView.swift:295-315,476-490` selects that exact email, but the design passes `selectedConversation.newest` to the detail view, and `ThreadDetailView.swift:237-272` has no selected-member focus or scroll input — pass the selected msgId through and focus that message in the thread; verify a search jump to an older member opens that member in view.
[P1] (confidence: 9/10) Non-goals / Design: Mark as read — “until the conversation is selected again” is not achieved when an unread member arrives in an already selected row: tapping it sets the same `newest.id`, so `onChange(of: selectedEmailId)` at `MainView.swift:240-249` never fires — handle a same-row tap explicitly when unread, or specify that the user must leave the row and return and test that path.
[P1] (confidence: 9/10) Design: UnifiedMailbox — recomputing conversations only “at the end of every `rebuildEmails`” misses the full-sort branch, which assigns `emails` and returns at `UnifiedMailbox.swift:69-75`; folder switches and large updates would leave rows from the previous view — recompute on both the full-sort and incremental paths, preferably from a single finalized email snapshot, and test a folder switch that takes the full-sort branch.
[P1] (confidence: 9/10) Testing — no test exercises the promised whole-conversation action routing or partial failure behavior; existing `MessageListTests.swift:149-243` only invoke standalone closures and cannot prove the UI or `MainView` invokes a manager method for every member — add an XCTest integration check with a two-member group and mocked manager responses: archive both IDs, fail the second, and assert only that member returns in Inbox and the first remains in Archive; also check keyboard and detail-button routing.
[P2] (confidence: 10/10) Design: Actions on a conversation / Error handling — “a member whose call fails is reverted” is false for archive, delete and spam: `GmailAPIManager.swift:750-765` treats HTTP 404 as successful removal and never throws — state the 404 exception explicitly and test one 404 plus one non-404 failure in a group.
[P2] (confidence: 9/10) Design: Model — “ties keep the input order (stable), so the output is deterministic” does not follow: unified input for all accounts comes from unordered dictionary values at `UnifiedMailbox.swift:42-46`, and the incremental insertion path at `:91-96` can give tied dates a different order than a full rebuild — define a stable secondary key such as accountId/msgId (and member order), then test equal-date messages across accounts and rebuild paths.
[P2] (confidence: 8/10) Design: UnifiedMailbox — the claimed `O(n)` regrouping is incorrect if messages and conversations are each sorted as required; sorting is `O(n log n)` in the general case — preserve the existing date-sorted `emails` order while grouping when possible, or state the actual cost and its acceptable bound.
[P2] (confidence: 8/10) Scope challenge / Scope — this design touches at least ten files including the Xcode project and tests, while the Goal is one-row presentation; adding a separately published projection and new model/test files expands the change without establishing a need — put the pure grouping type in an existing compiled model file, derive the list projection from the mailbox’s existing published emails, extend existing test files, and split broader detail-panel eligibility into a follow-up if the Goal is the only delivery gate; that split must revise `Decisions: When should the detail panel show ThreadDetailView (all thread messages) instead of the single-message view? (auto)`.
[P2] (confidence: 8/10) Testing — the checks do not cover the specified reply target, older-member selection navigation, or account-qualified detail behavior — add XCTest cases for adjacent navigation from an older member and newest-member reply targeting, plus a manual check with expected account-specific thread content after switching accounts with the same threadId.

## Section notes
### 0. Scope challenge
Existing `UnifiedMailbox.emails`, `MessageList` rendering, `MainView` selection/actions, manager per-message calls, and `ThreadDetailView` already cover most of the path. A smaller implementation can reuse them and Swift’s `Dictionary(grouping:by:)`; the spec introduces no distribution artifact. The detail heuristic broadening can be separately planned if the recorded decision is updated.
### 1. Requirements
The jump-to-specific-message and same-row reselect promises are incomplete. The unconditional per-member revert statement contradicts the existing 404 path. No placeholders were found.
### 2. Scope
Grouping, bulk actions/read behavior, and detail eligibility span distinct behavior changes; split the detail eligibility work if the delivery target is strictly a grouped row. Drafts, Outbox, search results, and message-count badges are explicitly excluded.
### 3. Feasibility
The named interfaces exist, and `moveEmailInMemory` does drop `threadId`, `to`, and `cc` at `GmailAPIManager.swift:820-831`. The project file registration, early return, local-only multiplicity check, cross-account view identity, and 404 exception need correction. Network thread fetch already has a retry UI at `ThreadDetailView.swift:148-160`.
### 4. Testability
The proposed XCTest suite covers pure grouping and mailbox projection. It does not verify the end-to-end action, selection, reply, and account-switch claims; the manual Dispute check covers only the happy path.
### 5. Decisions
The folder-local, newest-row, message-count, selected-email-ID, and per-message-call choices fit the repository. The automatic all-thread detail decision conflicts with a predicate based solely on loaded local messages; the user choices do not conflict with repository facts.
